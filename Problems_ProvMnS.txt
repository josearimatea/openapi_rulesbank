          memória);

      right-wins já faz o merge; file vazio -> file cheio).

3.22 PARÂMETRO DE OPERAÇÃO ENDEREÇADO NO PATH (20/set/2026)
MAIOR IMPACTO MEDIDO DO LADO DO GERADOR: 18 folhas de contrato perdidas, de 28
perdidas na execução.

NÃO É O §1.1 (aquele era QUAL path, e está consertado). Este é o NÍVEL: o path
está certo, falta o método. Em OpenAPI, `parameters` no nível do path vale para
TODOS os métodos; no nível da operação, só para aquele.

  #9   rule_text      : "The HTTP GET operation supports an optional query
                         parameter named scope of type Scope, using form style
                         with explode=true."
       openapi_object : paths./{className}={id}
       openapi_field  : parameters[in=query,name=scope]
       deveria ser    : paths./{className}={id}.get

9 REGRAS AFETADAS, EM DOIS FORMATOS:
  (a) query_parameter, seção 149 — 5 regras: scope, filter, attributes, fields,
      dataNodeSelector. Todas dizem "The HTTP GET operation supports..."
  (b) path_operation, seção 147 — 4 regras: put, get, patch, delete. Aqui o
      método foi para o openapi_FIELD em vez de compor o openapi_OBJECT:
        object=paths./{className}={id}  field=put
      Mesma confusão de nível, tipo diferente.
Todas passaram na validação (validation_passed: true).

NÃO É ERRO DE LEITURA — a spec atribui esses parâmetros ao GET e as operações ao
path. O erro é na tradução texto -> endereço.

O EXTRACTOR SABE FAZER CERTO, 3 contra-exemplos no MESMO banco:
  #52  query_parameter filter   -> paths./{className}={id}.delete  OK (operação)
  #5   path_parameter className -> paths./{className}={id}         OK (path)
  #6   path_parameter id        -> paths./{className}={id}         OK (path)
A #52 tem a MESMA forma das 5 defeituosas e mapeia certo. className e id ficam
no path porque realmente valem para todos os métodos.

O YAML CONFIRMA:
  /{className}={id}:
    parameters: [className, id]        # nível do path
    get:
      parameters: [scope, filter, attributes, fields, dataNodeSelector]

CONSERTO (determinístico, sem custo de LLM, em rules_check.py):
  para cada regra path_parameter | query_parameter:
      se rule_text cita método HTTP e openapi_object NÃO termina em .<método>:
          divergência
  VERIFICADO contra este banco: pega exatamente as 5, deixa passar as 4
  corretas. Zero falso positivo, zero falso negativo. O critério "o texto nomeia
  um método" é textual e verificável, não inferência — é o que o torna seguro.
  Para o caso (b) a checagem é outra: path_operation legítimo TEM o método no
  field, então o teste é se object já contém o método OU o field é um método,
  nunca os dois no mesmo nível.

HIPÓTESE (não investigada): as seções 147 e 149 estão AMBAS na lista das 11 que
esgotaram as 3 tentativas (§3.18 do legado: 147,148,149,152,160,162,166,172,
175,189,192). As duas seções deste defeito passaram pelo force-include, onde a
regra entra sem o mapeamento ter convergido. Vale checar se é defeito de
mapeamento em geral ou efeito do esgotamento.

RELACIONADO: §3.5 olhou EXATAMENTE estes parâmetros, viu que faltavam style e
explode, e não viu que o endereço estava no nível errado. E o §1.1, enquanto
mandava o path errado, ESCONDIA este defeito: não se olha o nível de um endereço
que já está errado. Segundo caso do padrão "conserto revela defeito atrás de si"
(o primeiro é o §3.25).


3.27 DUAS REGRAS DISPUTANDO O MESMO ENDEREÇO NÃO SÃO DETECTADAS (15/set/2026)
Descoberto no PerfMnS de agosto: DUAS regras para PerfMetricDirection::enum,
mesmo object E mesmo field, uma com value=[UP] e outra com [DOWN]. Ambas
passaram (score 1.0 e 0.98). Aplicando o banco literalmente, a segunda
sobrescreve a primeira e sai um enum com um valor só. Já corrigido no resultado

CRITÉRIO DE GRANULARIDADE (genérico, vale para qualquer MnS):
  cada item tem seu próprio openapi_field -> UMA REGRA POR ITEM
    ex.: properties.thresholdValue, properties.hysteresis
  os itens dividem o MESMO openapi_field  -> UMA REGRA SÓ, lista completa

A granularidade é decidida pelo DESTINO, não pela fonte. No texto 3GPP, UP e
DOWN são duas linhas de tabela com descrições próprias — o Extractor leu certo
(source_name=UP / =DOWN). O erro foi de mapeamento.

A FAZER: recusar duas regras com a mesma tripla (rule_type, openapi_object,
openapi_field) quando o campo for de valor-coleção. Nada em rules_check.py faz
isso; a checagem de duplicata que existe compara o CONCEITO da notificação
(derrubou o 6º callback do ProvMnS), não o par objeto+campo.
