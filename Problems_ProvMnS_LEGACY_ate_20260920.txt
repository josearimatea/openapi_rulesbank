Análise: 97 regras ProvMnS × TS28532_ProvMnS.yaml
Antes das três seções, uma correção ao que eu disse antes: /eventListener não é contaminação de outro MnS. A seção 393 é 12.1.2.2.1.1, dentro de 12.1.2 RESTful HTTP-based solution set for integration with ONAP VES API — uma solution set alternativa do próprio ProvMnS, que não está no YAML. O problema é outro, e explico na seção 2.

1. Problemas nas regras geradas
Regras que existem e correspondem a algo real no YAML, mas estão mapeadas errado.

1.1 Fragmentação de path — o defeito estrutural dominante
O YAML tem um único path: /{className}={id}. As regras usam cinco formas diferentes para referenciá-lo:

Forma usada	Regras	Situação
paths./{className}={id}	16	✅ canônica
paths.{MnSRoot}/ProvMnS/{MnSVersion}/{URI-LDN-first-part}/{className}={id}	15	❌ URI literal do documento
paths./{notificationTarget}	6	✅ (callback — ver 3.1)
paths./{MnSVersion}/{URI-LDN-first-part}/{className}={id}	2	❌ fragmento intermediário
paths./eventListener	1	⚠️ solution set ONAP VES
18 das 40 regras de path estão fora da chave canônica.

Causa: o Extractor copia a URI literal da cláusula do documento (ex.: 12.1.1.3.2.1.2 URI traz {MnSRoot}/ProvMnS/{MnSVersion}/{URI-LDN-first-part}/{className}={id}) em vez de normalizá-la para a chave de paths do YAML. O YAML coloca a parte fixa em servers/base URL e mantém só /{className}={id} como path.

Consequência em cadeia: como cada seção decide isoladamente, a mesma operação HTTP acaba em chaves distintas — e a deduplicação entre seções não consegue enxergar as duplicatas, porque openapi_object difere. É provavelmente por isso que a validação cruzada deixou passar as duplicações abaixo.

1.2 Operação PUT com responses divididos em três lugares
O PUT do YAML tem 200, 201, 204, default. As regras produziram:

Seção 355 → 200, 201, 204, 4XX, 5XX em paths./{className}={id}.put ✅
Seção 335 → default no mesmo path — marcada validation_passed: false, com nota do Validator: "do not use default with a oneOf to combine the successful Resource response and…"
Seção 336 → 400 em paths./{MnSVersion}/...patch (path fragmentado)
Três seções do documento (12.1.1.1.4.1, 12.1.1.3.2.1.3.1 e 12.1.1.1.4.2) descrevem as mesmas operações sob ângulos diferentes, e cada uma gerou seu próprio conjunto sem consolidação.

1.3 DELETE inteiro no path errado
Todas as 5 regras da seção 358 (12.1.1.3.2.1.3.4 HTTP DELETE) usam a URI completa. São regras corretas em conteúdo — 200, 204, 4XX, 5XX — mas nenhuma aterrissa em paths./{className}={id}.delete, que é onde o YAML as espera.

1.4 Path parameters que não são parâmetros
A seção 331 gerou 5 path_parameter: MnSRoot, MnSVersion, URI-LDN-first-part, className, id.

No YAML só existem dois (linhas 26–36): className e id. Os outros três compõem a base URL, e o próprio documento os define por referência à TS 32.158 — não são parâmetros de path da operação. São 3 regras a mais (ver 2.3), e as 2 corretas estão no path errado.

2. Regras que não deveriam estar
2.1 As 5 já marcadas pelo próprio Validator (validation_passed: false)
O pipeline as detectou e rejeitou 3× cada, mas o Builder as incluiu por esgotamento do orçamento de tentativas (MAX_ITERATIONS). O mecanismo funcionou — a marcação está correta:

Seção	Regra	Diagnóstico do Validator
358	request_body deleteMOI	"absence of a request body is not a valid OpenAPI request_body rule" — o texto extraído era literalmente "data type is n/a"
335	response default	mapeamento default + oneOf inválido
372	schema_property op	duplicata de regra já validada
372	schema_property insert enum	pertence ao schema Insert, não a MoiChange
384	schema_property SourceIndicator	é o schema em si, não properties.SourceIndicator
A 358 é notável: o Extractor transformou a ausência de request body numa regra de request body. É o inverso do bug conhecido de request_body sumindo.

--- CAUSA DAS DUAS DA SEÇÃO 372 (investigada em 01/set/2026) — PARA CONSERTAR ---

Nada a ver com path: o openapi_object é o mesmo (components/schemas/MoiChange)
em todas. São dois defeitos distintos em schema_property:

(a) ENUM NO SCHEMA ERRADO. No YAML, MoiChange.op é uma REFERÊNCIA:
        op:     { $ref: '#/components/schemas/Operation' }
        insert: { $ref: '#/components/schemas/Insert' }
    O enum pertence aos schemas Operation e Insert, que têm suas próprias
    cláusulas de definição. A tabela 3GPP de MoiChange lista o atributo `op` com
    seus valores permitidos, e o Extractor colapsa isso num `enum` dentro de
    MoiChange em vez de emitir o $ref. É o que o Validator apontou:
    "the enum constraint belongs in the separate Type Insert schema-definition
    section, not in the Type MoiChange schema".
    O Extractor não distingue "atributo que referencia outro schema" de
    "atributo com enum próprio" — a correção é na definição de schema_property,
    dizendo quando emitir $ref em vez de enum.

(b) DUPLICATA LITERAL. `enum` emitido duas vezes para o mesmo `op`, mesmo
    openapi_object, mesmo openapi_field. Puramente redundante.

Medido sem Validator (tests/investigation/provmns/test_gap_retrieval.py,
01/set/2026): a seção produziu 17 regras cruas, com `op` três vezes e `enum`
repetido — contra 13 no run completo, onde o Validator pegou parte delas. Como
aquele teste não roda o Validator, os números não são comparáveis: se o aumento
é ruído entre execuções, efeito das mudanças de prompt do dia, ou ausência de
validação, não foi investigado.

2.2 Passaram como válidas, mas não correspondem ao YAML
Estas são mais preocupantes, porque nenhum estágio as pegou:

response 400 (seção 336) — o YAML nunca usa códigos de erro específicos; só default. O texto de origem diz "such as HTTP 400", ou seja, um exemplo no documento virou regra normativa.
query_parameter scope no DELETE (seção 358) — duplica o scope do GET (seção 333) e o atribui ao DELETE, que no YAML não tem query parameters.
path_operation notifyMOICreation em /eventListener (seção 393) — pertence à solution set ONAP VES (12.1.2), que não é coberta por este YAML. Não é erro de extração: a regra descreve fielmente o documento. É erro de escopo — o TS28532_ProvMnS.yaml cobre apenas a solution set RESTful de 12.1.1.
2.3 Path parameters inexistentes
MnSRoot, MnSVersion, URI-LDN-first-part (seção 331) — 3 regras marcadas válidas para parâmetros que o YAML não declara.

Total estimado a mais: 12 regras (5 já marcadas + 7 que passaram indevidamente).

3. Regras que faltaram
3.1 Os 4 callbacks do PUT — a maior lacuna
O YAML define, dentro do PUT (linhas 86–173), quatro callbacks, cada um com requestBody e responses próprios:


callbacks:
  notifyMOICreation:
    '{request.body#/notificationRecipientAddress}':
      post:
        requestBody: {...NotifyMoiCreation}
        responses: {'204', default}
Nenhuma regra os mapeia como callbacks. As 6 regras em paths./{notificationTarget} descrevem a mesma coisa, mas como path de primeiro nível — o que é justamente o que o commit b6be728 ("Notification is a callback only when the consumer hosts the endpoint") deveria decidir. Aqui a notificação é hospedada pelo consumer, então deveria ter virado callback e não virou.

Faltam: a estrutura callbacks, a expressão {request.body#/notificationRecipientAddress}, e os requestBody/responses dos 3 outros callbacks (só notifyMOICreation tem regras).

--- CAUSA-RAIZ (investigada 01 e 07/set/2026) — É INFERÊNCIA, NÃO RECUPERAÇÃO ---

O prompt exige openapi_object = "paths.<path>.<method>.callbacks.<nome>". A seção
que descreve o POST (365) não nomeia a operação dona, e o Extractor recua para
path_operation em paths./{notificationTarget} — a string que o próprio prompt
declara errada. Runs do PerfMnS chegaram a emitir os literais "<owning-path>" e
"<subscription-path>": ele aceita que é callback e não consegue preencher o
âncora.

O que foi verificado, em ordem:

  1. O fato basta. Teste A/B (test_notification_as_path.py): a MESMA seção 365,
     com UMA frase nomeando a operação dona, passou de 4 regras erradas para 16
     em paths./{className}={id}.put.callbacks.<nome>.post, com os 4 nomes reais.

  2. O fato existe e é recuperável. A cláusula 12.1.1.3.2.4.2 remete a
     "notificationRecipientAddress defined in clause 4.3.22.2 in TS 28.622", e o
     corpus tem essa cláusula: "To receive notifications, a MnS consumer has to
     create an NtfSubscriptionControl instance on the MnS producer".
     (Antes eu havia concluído que só existia no Annex A — errado, busquei só a
     string exata no 28532 e não testei o corpus.)

  3. O pipeline recupera. A Fase 1 do pré-analisador detecta a referência e faz
     um RAG por referência; para a 363 ela traz ~22k chars COM o
     NtfSubscriptionControl e a frase "has to create".

  4. A Fase 2 agora registra e propaga (cross_refs, implementado em 07/set). A
     seção 365 recebe, literalmente:
       "To receive notifications, an MnS consumer has to create an
        NtfSubscriptionControl instance on the MnS producer"
       "notificationRecipientAddress belongs to the NtfSubscriptionControl object"

  5. E o Extractor NÃO usa. Com os dois fatos em mãos, as três tentativas
     emitiram paths./{notificationTarget} com notifyEvent.

O passo que falta não está em documento nenhum: "o consumer cria uma instância"
-> "criar, neste serviço, é o PUT em /{className}={id}" -> "logo o callback
ancora ali". O ProvMnS não tem cláusula de subscription própria (verificado: não
há 12.1.1.x de subscription), então a ponte é modelagem, não texto.

Consequência: mais contexto recuperado não resolve. As saídas possíveis são dar a
convenção no prompt ("um callback ancora na operação que cria o recurso que
origina a notificação") ou deixar o âncora sem resolver e fechá-lo numa etapa
posterior, ao montar o YAML.

--- ÂNCORA RESOLVIDA EM 13/set/2026 (a primeira saída, a convenção) ---

A cascata da Fase 2 passou a resolver o âncora de forma determinística. Resultado
do teste de 4 seções (12.1.1.1.2, 12.1.1.3.2.1.3.1, 12.1.1.3.2.4.2,
12.1.1.3.2.4.3.1):

  [analyzer 363] callback anchor: 'paths./{className}={id}.put' (from convention)
  [analyzer 365] callback anchor: 'paths./{className}={id}.put' (from convention)
                 (idêntico nas 3 tentativas da 365)

Confere com o oficial: os callbacks estão em paths: '/{className}={id}': put:
(linhas 25/37/86). A seção 365 fechou com 18 regras, 17 ancoradas como callback,
0 em paths./{notificationTarget}. Os 4 nomes de callback saíram certos.

DE QUEM ERA A CULPA (a pergunta que orientou a investigação): de nenhum dos
agentes. O RAG achou, a Fase 1 detectou, a Fase 2 registrou, o reducer propagou e
a lista de irmãos entregou — verificado nos logs, os cross_refs chegam à 365. O
defeito estava no PROMPT da cascata, em dois passos que eu mesmo escrevi:

  - o passo 2 perguntava "qual operação carrega o campo de endereço no request?".
    A entrada do irmão diz "maps createMOI: put /{className}={id}" e nada mais;
    para concluir o resto era preciso encadear três fatos de três cláusulas.
  - o passo 3 (convenção) repetia a mesma exigência ("ancore na operação que CRIA
    o recurso que carrega o campo de endereço"), então caía no mesmo buraco e ia
    para o passo 5, 'unresolved'.

Com a regra "never assume" ativa, o agente se recusava a inventar e declarava a
lacuna — comportamento correto. O erro era pedir JULGAMENTO onde o pedido era
uma sequência de ifs.

CONSERTO: passo 2 restrito ao caso explícito (só quando uma cláusula NOMEIA a
operação); passo 3 virou lookup mecânico sobre a lista de irmãos ("a entrada cuja
operação cria uma instância de objeto gerenciado"), explicitamente dispensado de
provar que o corpo do create carrega o campo de endereço — suprir essa junção é a
função da convenção. Acrescentado que aplicar a convenção é seguir instrução, e
não supor, para não colidir com "never assume".

Junto: maps_path passou a descartar o "..." com que o título da cláusula abrevia a
base URL (o documento escreve Resource ".../{className}={id}", a chave do YAML é
/{className}={id}). Antes a Fase 2 gravava o "..." literal.

DEFEITOS QUE RESTAM nos callbacks (do teste de 13/set):

  a) request_body DUPLICADO para o AttributeValueChanges — a mesma notificação
     emitida duas vezes, sob dois nomes:
       callbacks.notifyMOIAttributeValueChanges  (correto, veio do âncora)
       callbacks.notifyAttributeValueChanges     (não existe em YAML nenhum)

     CAUSA, em três passos:

     1. O documento tem DUAS fontes para o nome, e elas discordam. O heading
        "12.1.1.2.4 Notification notifyMOIAttributeValueChanges" dá o nome
        canônico do callback; a tabela 12.1.1.3.2.4.3.1-2, que é a única coisa que
        a seção 365 tem no próprio corpo, escreve o tipo como
        "NotifyAttributeValueChanges" — sem o MOI. Essa grafia é lapso de redação
        da 3GPP (detalhado em 3.7: uma ocorrência contra 22 das formas corretas,
        persistente em i00/i20/k00).

     2. O prompt autorizava as duas. O bloco source_name do rule_type callback
        mandava copiar o nome "de onde quer que a spec o escreva — esta seção, uma
        tabela de mapeamento no contexto, ou a memória de referência". A tabela da
        própria seção se encaixa nessa lista, então a grafia errada era fonte
        legítima pela instrução que existia.

     3. Com duas fontes válidas e divergentes, o Extractor não escolheu: emitiu sob
        as duas. Não é o modelo inventando nome — é o prompt não ter estabelecido
        precedência entre fontes, do mesmo modo que a cascata do âncora não tinha
        (ver a lição registrada acima).

     Os outros três callbacks saíram sem duplicata porque para eles a tabela e o
     heading concordam no MOI — só esta linha da tabela diverge.

     DECISÃO (13/set/2026): não perseguir o nome certo. O erro é da 3GPP e não é
     nosso para consertar. O inegociável é NÃO DUPLICAR — uma regra por
     notificação. Sair com o nome errado é aceitável, de preferência com score
     baixo; se o agente perceber a divergência e escolher o heading, melhor ainda,
     mas não é requisito.

  b) path_operation sobrando: "paths./{className}={id} post". O YAML não tem post
     nesse path. É resíduo do comportamento antigo (notificação virando operação
     de primeiro nível); mudou de path, mas não desapareceu.

  c) notifyMOIChanges sem o segundo media type: o YAML dá application/json E
     application/yang-data+json para esse callback; saiu só um request_body.

  d) capitalização dos schemas: saíram NotifyMOICreation / NotifyMOIDeletion /
     NotifyAttributeValueChanges, enquanto components usa NotifyMoiCreation,
     NotifyMoiDeletion, NotifyMoiAttributeValueChanges (linhas 444-491). Mesma
     raiz de (a): o nome foi copiado da tabela do documento em vez de normalizado
     para a chave do YAML. No run completo de 28/ago esses nomes saíram CERTOS,
     então é regressão do recorte ou instabilidade, não defeito permanente.

NÃO é defeito: 4XX/5XX no lugar de 'default' nas respostas dos callbacks. Vem da
referência OpenAPI e é convenção adotada.

A única regra de request_body do PATCH (seção 336) menciona apenas application/merge-patch+json, e está no path fragmentado. Os outros três, incluindo os que usam array(PatchItem) como schema, não aparecem.

3.9 Duas regressões do próprio conserto, e a causa comum (14/set/2026)
A rodada que validou 3.8 (correções 19->2, todas nomeando valor, 365 com 18 regras
e 18 callbacks numa tentativa só) trouxe DUAS regressões. As duas têm a mesma
assinatura das falhas anteriores: um critério que o agente consegue conferir
LOCALMENTE vencendo o critério que exigiria buscar a fonte.

REGRESSÃO 1 — a grafia sem MOI voltou, e agora SUBSTITUIU a canônica.
Na 365 saíram 5 regras sob callbacks.notifyAttributeValueChanges e
notifyMOIAttributeValueChanges apareceu ZERO vezes. O Reflector aprovou com 0.94
citando a minha própria regra: "The notification name uses the required
lowerCamelCase form, notifyAttributeValueChanges".

  CAUSA EXATA: a regra escrita em 13/set define o nome por FORMA
  ("a NOTIFICATION is lowerCamelCase, keeping the acronyms"). A grafia errada da
  tabela SATISFAZ essa forma. E verificado no documento: a seção 365 não contém
  'notifyMOIAttributeValueChanges' em lugar nenhum do seu corpo — o nome canônico
  só existe no heading 12.1.1.2.4, outra cláusula. Reflector e Validator recebiam
  apenas o conteúdo da seção, então só podiam conferir forma, nunca origem.
  Antes do commit c999803 não havia regra de forma e o nome saía certo: é
  regressão introduzida pelo conserto.

REGRESSÃO 2 — o Validator mandou quebrar a âncora.
Instrução emitida: "Fix openapi_object to paths./{className}={id}.post.callbacks.
notifyMOIDeletion" — .post onde a âncora resolvida é .put. Se aplicada, desfaria o
conserto de 3.1.

  CAUSA EXATA: verificado no documento, a seção 365 menciona "POST" 3 vezes e
  "PUT" zero. O Validator, com apenas o conteúdo da seção, viu um callback em .put
  e "corrigiu" para o método que o texto menciona. Ele NÃO recebia a âncora: o
  verdict_update nem sequer gravava callback_anchor no estado, e
  format_section_verdict expunha só section_kind, is_schema_home, base_ref e
  inherited_fields. A seção descreve como a notificação é ENTREGUE (POST); a
  âncora é a operação pela qual o consumidor FORNECEU o endereço (PUT).

AUDITORIA DO CONTEXTO (o que cada nó recebia):
  Extractor: section_analysis (guidance completo com a âncora), cross_ref_context,
             stage2/stage3_context, candidate_rules, skip_rules, sibling_summary.
  Reflector: section_verdict (pobre), sibling_rules (as outras REGRAS da seção,
             não as cláusulas), section_content, helper_context, contract_summary.
  Validator: os mesmos do Reflector + declared_gaps.
  Ou seja: quem JULGA recebia menos que quem PRODUZ, e justamente as peças que
  decidem nome e âncora.

CONSERTO:
  1. verdict_update passou a gravar callback_anchor e callback_anchor_source.
  2. format_section_verdict (parsers.py) passou a expor a âncora — com a
     advertência de não reescrever o método para o que a seção menciona — e o
     "this clause maps: <op> -> <method> <path>". Ponto único: serve o Reflector
     (2 chamadas) e o Validator (1).
  3. _build_sibling_summary MOVIDA de extractor.py para parsers.py como
     build_sibling_summary (apagada da origem; test_spec_references.py atualizado).
     Agora os três nós usam a mesma. É a única fonte onde o nome canônico aparece
     inteiro ("12.1.1.2.4 Notification notifyMOIAttributeValueChanges").
  4. Reflector e Validator passaram a receber {sibling_summary} no prompt.
  5. A regra de nomes foi invertida nos dois: a FONTE é o heading; a forma virou
     apenas CONFERÊNCIA ("a spelling can have the right form and still be the
     wrong name"). Um nome que não casa com heading nenhum não pode ser usado.

3.8 O loop de correção não corrigia nada (investigado e corrigido 13/set/2026)
Achado ao investigar por que a seção 355 caiu de 4 regras para 2. São DOIS
defeitos somados, ambos meus, e ambos posteriores ao run de 28/ago — naquele run
a colisão não existe (97 regras, apenas 1 com score>=0.8 reprovada, e essa
legitimamente).

DEFEITO A — COLISÃO ENTRE DOIS BLOCOS DO VALIDATOR.
O Extractor é OBRIGADO a reportar quando preenche um campo por convenção
("a field filled by default and left unreported is a value nobody will ever
verify"). Obedeceu: emitiu application/json e declarou a lacuna. Aí o Validator
tinha duas instruções incompatíveis:

  "A VALUE THE CLAUSE DOES NOT SPELL OUT IS NOT AN INVENTION"
      -> valor vindo da referência é correto, não rejeite
  "RULES BUILT ON A DECLARED GAP — do not pass them"
      -> toda regra que uma lacuna toca vira correction

A segunda venceu. Resultado medido na rodada de 13/set:
  - 12 das 19 reprovações foram por lacuna declarada (8 de media type, 4 de
    ErrorResponse), em 332, 355 e 365;
  - 332 request_body reprovado nas 3 tentativas, com o Reflector ficando MAIS
    confiante a cada uma (0.88 -> 0.92 -> 0.95, flagged=False nas duas últimas);
  - 355 request_body idem (0.88, 0.88);
  - 332 tentativa 3: o Extractor emitiu 200 E 201; o Validator mandou trocar 200
    por 201 e reprovou TAMBÉM a 201 — as duas caíram, e o YAML tem as duas.
    Ali nem havia lacuna de media type envolvida: uma lacuna declarada na seção
    envenenava todas as regras daquela tentativa.

DEFEITO B — A INSTRUÇÃO NÃO NOMEAVA VALOR.
O bloco da lacuna mandava "an instruction naming the fact to apply" — o FATO, não
o VALOR. Saíram instruções como "apply the declared media-type gap", "rebuild
using the OpenAPI/reference convention", "resolve the declared request-media-type
gap". Nenhuma diz QUAL media type. O Extractor relê a mesma cláusula silenciosa, a
convenção só oferece application/json, ele re-emite application/json, e leva outra
reprovação. Compare com a única que funcionou: "Fix openapi_field from 200 to 201"
— nomeia origem e destino, é acionável.

O mecanismo de entrega está correto e não era o problema: _build_correction_task
monta RULES TO CORRECT com rule_text, rule_type, source_name e a instruction, e o
log confirma "Retry 2 for [332] — 1 error(s)". O Extractor RECEBEU. Não tinha o
que fazer de diferente com "aplique a convenção" se foi a convenção que produziu o
valor.

CONSERTO (as duas pontas, nos três nós):
  Validator - o bloco da lacuna trocou o gatilho "existe lacuna declarada" pela
              pergunta que separa os casos: a lacuna deixou o mapeamento
              INDETERMINADO (nada supriu o valor -> correction, nomeando o valor)
              ou apenas registra que um PADRÃO FOI APLICADO (a cláusula é muda e o
              valor veio da convenção, como instruído -> valid=True, a lacuna é
              nota de auditoria)?
            - o campo instruction passou a exigir o VALOR LITERAL, com exemplo do
              que não vale ("Apply the declared media-type gap"). Se não souber
              nomear, não emitir correção vazia: deixar valid=True e registrar em
              new_missing_rules.
  Reflector - ao julgar um valor errado, NOMEAR o certo no reasoning; é de lá que
              o Validator tira o valor para a correção.
  Extractor - onde a correção nomeia um valor, escrever aquele valor: ele vence a
              convenção e a referência, que são o padrão de campo ainda não
              decidido. Se a instrução não nomear valor, manter a regra e dizer em
              missing_context que a correção não nomeou valor.

ONDE essa regra do Extractor foi escrita, e por quê (a pergunta não é óbvia):
NÃO existe prompt separado para retry. Há um único extractor_prompt
(_SYSTEM + _USER, extractor_prompts.py:685) e o retry é o MESMO prompt com
{correction_task} preenchido — vazio na primeira tentativa. Então a regra foi para
o cabeçalho que _build_correction_task gera (extractor.py), não para o _SYSTEM:

  - o _SYSTEM é lido em TODA extração, inclusive nas centenas de primeiras
    passadas em que não há correção alguma — a regra seria ruído permanente;
  - o cabeçalho já governa esse bloco ("Return ONLY the rules listed under RULES
    TO CORRECT..."), então é onde uma instrução sobre COMO OBEDECER uma correção
    pertence;
  - fica adjacente ao RULES TO CORRECT que ela rege, e não a ~400 linhas dele.

Junto foi preciso reescrever o bloco ANSWERS TO WHAT YOU REPORTED MISSING do mesmo
cabeçalho: ele dizia "Apply the fact to the rules that gap affected" — exatamente a
formulação "aplique o fato" que este conserto elimina. Deixá-lo intacto
reproduziria dentro do Extractor a mesma colisão recém-consertada no Validator.
Agora ele manda procurar um VALOR CONCRETO no bloco recuperado, escrever esse
valor, e — quando o bloco não fixa valor nenhum — manter a regra e voltar a
reportar a lacuna, deixando explícito que um valor vindo de convenção não é o que
esses blocos existem para derrubar.

4.1 O CASO notifyEvent — RESOLVIDO EM 09/set/2026

Entre as capabilities do ProvMnS estava:
